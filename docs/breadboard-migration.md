## 目标与保护边界

同时支持原有正点原子 BOX 和新的 ESP32-S3 面包板原型；通过独立板型配置和独立构建目录区分驱动、引脚及产物。新板暂不接业务按键。此处记录迁移准备，不代表已实现双板支持。

2026-09-17 检查时工作区干净，源码基线为 `685118ccc961d3fda70db7fdf1a8a5ff2d0b9f2c`。已归档至 `.probe/hardware-migration-backup/alientek-source-685118ccc961.tar.gz`，该本地目录不提交 Git。当前工作树未发现 `firmware/build` 下可归档的固件二进制；源码归档不能替代设备 Flash 备份，设备现有固件及语音包备份仍待完成。尚未对设备执行擦除或烧录。

- 正面从左到右引脚为 `GND VCC SCL SDA RES DC CS BLK`；背面视角顺序相反。接线必须按丝印，不按照片左右方向记忆。

- 功放模块丝印为 `MAX98357A`；麦克风具体型号、扬声器阻抗和功率待确认。
- 现有面包板接线未经核验，不从线色或遮挡照片推断网络。
- 用户确认当前电脑连接的是正点原子设备；新开发板尚待单独连接确认。

## 新开发板 USB 首次连接

用户随后拔掉正点原子、接入新开发板 OTG 口。当前枚举为 Espressif `USB JTAG/serial debug unit`，VID:PID `303A:1001`，序列号 `D0:CF:13:15:27:E4`，串口 `/dev/cu.usbmodem8401`。这证明新板原生 USB 枚举正常，不证明外设、存储或现有程序正常。串口路径和 VID/PID 可与旧板相同，切换设备不能仅凭路径识别个体。

`lsof` 显示现有 `vibebuddy` 进程正在占用该串口；尚未打开串口进行 ROM 查询、Flash 读取或烧录。需要先释放端口，再读取芯片信息及保存旧程序。正点原子设备 Flash 备份仍待重新连接时完成。

1. 保留正点原子源码、确认原设备固件备份，再切换设备。
2. 新板断电，移除外设及电源轨连接线，仅保留主控开发板；核对面包板孔位无电源短接，再接单根 USB 数据线。识别端口和芯片，确认旧程序是否需要保存。

## 正式固件迁移（2026-09-17）

已新增 `breadboard` 板型，保留默认 `alientek` 板型。原 BOX 本轮没有连接、擦除或烧录；原音频、显示和按键路径保留。用户此前取消了备份，本轮未继续读取 Flash；开头的备份待办是历史状态，不是本轮前置条件。

分别构建：

```bash
bash tools/build-firmware.sh alientek
bash tools/build-firmware.sh breadboard
```

各自产物和 sdkconfig 位于 `firmware/build-alientek`、`firmware/build-breadboard`。脚本仅编译；烧录前必须重新核对串口与设备 MAC，不能以端口名称判断设备身份。旧 `tools/flash.sh` 仍是默认 BOX 入口，不能用它烧录面包板。

面包板复用已验证的屏幕与功放引脚，不需改线。SPI 频率仍为 4 MHz。所有原有页面先按 4:3 比例缩至 240×180，在 240×240 屏幕上下留边；采用面积采样避免小字整条笔画丢失。此为功能迁移版，小字仍比原屏小，尚未单独重排方屏界面。BLK 接 3V3，熄屏和识别闪烁通过 LCD 显示开关实现，不等于切断背光供电。

MAX98357A 使用软件音量，App 的 20～100 档映射到 PCM 振幅的 1.25%～6.25%，默认 65 档约为 4.06%。此限制沿用已通过的低音量测试范围。未接业务按键，固件明确上报 `BUTTONS NOT FITTED`；不会读取 BOX 的按键扩展芯片。麦克风、Wi-Fi 语音对话尚未迁移或验收。

### App 和切换板型

App 根据设备上报的 `BOARD` 选择对应固件。旧 BOX 固件没有该字段时仍按 BOX 兼容。重新连接时清除上一台设备的板型、音量、音色等缓存。设备与请求板型不符时，daemon 拒绝烧录。截图链路支持 320×240 和 240×240。

`bash app/scripts/build-app.sh --debug` 已生成同时包含两种固件的 `app/build/Vibe Buddy.app`，本轮运行的就是这个包，没有替换 `/Applications` 下的 App。它仍使用原有 Hook 路径和本机配置。日常切换先断开当前板，再连接另一块，App 自动重连；不要同时插两台依赖自动选择。

## 麦克风采集测试

圆形模块已按引脚文字连接：VDD→3V3、GND→GND、L/R→GND、SCK→G15、WS→G16、SD→G17。具体芯片型号仍未确认；当前按 Philips I²S 数字麦克风接口验证。麦克风 SD 是数据输出，不能与 MAX98357A 的 SD 使能脚混接。

仅面包板编译 `agent_mic.c`，使用 I2S1；扬声器仍为 I2S0。`device.mic.capture` 命令采集两秒：16 kHz、左右各 32 位槽、每帧 64 个时钟，丢弃开始 128 ms，取左槽高 16 位。仅在命令期间打开采集，完成即关闭、释放通道。当前是同步硬件测试，录音及导出期间界面会短暂停止刷新，不是正式语音交互实现。

退出 App 释放串口后运行：

```bash
python tools/capture-mic.py /dev/cu.usbmodemXXXX .probe/mic/test.wav
```

需要 pyserial；脚本核对固件板型、倒数三秒、接收带偏移量的 Base64 数据，核对完整 64,000 字节后写本地 WAV，并输出峰值、去直流 RMS 和削波计数。不会上传录音。测试后重新打开本次构建的 App。

2026-09-17：两种板型构建通过。核对 MAC `d0:cf:13:15:27:e4` 后仅更新新板 app，哈希校验通过。首次两秒采样完整收到 32,000 点，最小 -133、最大 521、去直流 RMS 117.51、削波 0，保存于 `.probe/mic/baseline.wav`。这证明链路产生非恒定数据，尚不能单凭底噪认定语音录音通过；等待用户说话测试。

用户准备好后完成说话采样：`.probe/mic/speech.wav`，32,000 点，最小 -1168、最大 283、整段去直流 RMS 165.42、削波 0。按 100 ms 分块观察，开始有直流衰减，后半段 RMS 出现约 14～142 的变化，不能把整段 RMS 增长直接等同于清晰人声。保留原始文件，另生成 80 Hz 高通、16 倍增益的 `speech-listen.wav` 供用户试听；清晰度待确认。
