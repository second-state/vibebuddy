# Enabling XGGF speech recording and transfer — implementation plan

Branch: `xggf-64x8` only. Decisions locked with the user: (1) end state is **app-facing capture** — Record/Stop/playback/save in both the Mac and Linux Device pages, no speech recognition; (2) **app/daemon-initiated recordings only** (no device push-to-talk this round); (3) **strict gates-first sequencing** — reliability Gates 2–5 of `firmware-xggf/AUDIO_PROBE_PLAN.md` complete before any enablement code.

Current state: firmware captures 8/16 kHz left-channel I2S speech and streams numbered 20 ms base64 frames (`AUDIO BEGIN/FRAME/END`, `firmware-xggf/main/audio.c`) over USB and Noise-encrypted Wi-Fi TCP 7340; the daemon's `AudioIngestor` (`daemon/src/audio.rs`) reconstructs WAV behind token-gated endpoints (`daemon/src/main.rs:798-801`). USB is verified clean (5 s/30 s exact). Wi-Fi Gate 2 is unmet: intermittent fatal `recv_errno=113` with unknown initiator. Nothing consumes the WAV; both apps show "Voice… not yet supported" for XGGF.

## Phase 1 — Gate 2: attribute and fix the errno-113 Wi-Fi failure

Instrumentation first (no transport change), then one measured change at a time:

1. **Per-recording firmware counters:** `LINK DIAG` counters are cumulative across sessions, which blocked attribution (`WIFI_AUDIO_DIAGNOSTICS.md:100`). Snapshot all `wifi_link.c` diagnostics at `AUDIO BEGIN` and report **deltas** for that recording in the post-`AUDIO END` `LINK DIAG` (keep the cumulative line as well). Map the Wi-Fi reason code through the existing `wifi_failure_reason` table so the name, not just `5`, appears. Record last Wi-Fi disconnect time relative to recording start, and RSSI (`esp_wifi_sta_get_ap_info`) at BEGIN/END.
2. **Daemon-side close evidence:** the failing run captured no session-ending line (`WIFI_AUDIO_DIAGNOSTICS.md:126`). Verify the LAN/noise session teardown logs a sanitized close reason (initiator: protocol/EOF/TCP error); add it in `daemon/src/lan.rs`/`serial_transport.rs` if missing, and make `tests/audio_probe.py` always print those lines on failure.
3. **Packet capture attribution:** during repeat runs, `tcpdump` on the host Wi-Fi interface filtered to port 7340 (results under `/tmp`, like prior runs). This settles whether the RST/FIN originates from the daemon host and whether ICMP/802.11 events precede the firmware's `EHOSTUNREACH`.
4. **Single-change hypotheses, each re-tested with `--wifi-only --repeat=10`:**
   - H1 Wi-Fi modem power save (ESP32-C3 default) → association/ARP failure surfacing as `EHOSTUNREACH` on recv. Test `esp_wifi_set_ps(WIFI_PS_NONE)` (or `MIN_MODEM`); if it fixes, keep it and note the power implication for this duty device.
   - H2 Association loss precedes the recv error (per-recording counter ordering will show this): chase why the AP drops the client mid-burst (idle kick, RSSI); consider daemon-side TCP keepalive as the measured fix.
   - H3 Daemon-initiated reset (probe restart/teardown race): fix ordering if capture shows the host sending RST.
5. **Loop stop-rule:** max 3 consecutive repeat sequences per build before reassessing, honoring "testing was stopped to prevent a loop".

**Exit:** at least two independent 10/10 five-second 16 kHz Wi-Fi sequences on the fixing build, zero unexplained loss/duplication/reordering/disconnect, and every observed failure classified. Update `WIFI_AUDIO_DIAGNOSTICS.md` and `WORK_NOTES.md` with the attribution.

## Phase 2 — Gate 3: 30 s/60 s Wi-Fi streaming and resources

- Run `wifi-16k-30s` (probe's non-quick path), then extend the probe with a 60 s variant. Record heap/`heap_min`/stack headroom/`panel_us` (minute `DIAG`), raw slots, overruns, timing normalization frames, arrival intervals, end lag, RSSI trend.
- Panel/Wi-Fi interference check: compare a repeat sequence with the panel active vs. blanked.
**Exit:** bounded memory, no sustained backlog, no unexplained acquisition loss, documented timing (no synchronized-clock latency claims).

## Phase 3 — Gate 4: fidelity and recovery (hard user checkpoint)

- **Listening confirmation by the user:** replay known speech at 8/16 kHz over USB and Wi-Fi (existing `/tmp/xggf-speech.wav` + `aplay` stimulus); user confirms intelligibility. This gates everything after it.
- WAV property assertions: mono, 16-bit, exact rate/duration, `clipped_percent`, channel/bit alignment (host tests already pin the format).
- Physical recovery matrix: cancel mid-recording (DELETE → 409); intentional device unplug, Wi-Fi loss, daemon restart, and device reboot mid-recording — each must end with the terminal `last_error` on stats (409), no partial WAV retention, and a next-arm recovery. Malformed/oversized frames and unauthorized 401 remain covered by unit tests + the probe's existing assertions.
**Exit:** understandable speech end-to-end and every failure path rejects/discards safely.

## Phase 5 — Enablement: app-facing capture on both platforms

**Daemon:**
1. **Opt-in without a random token:** keep the five routes and the `VIBEBUDDY_AUDIO_PROBE_TOKEN` path unchanged; additionally allow recordings when a new documented `VIBEBUDDY_XGGF_AUDIO=1` is set (default off — the default-off, explicit-consent posture is preserved; XGGF-only 409, 60 s cap, in-memory, no audio logging all unchanged).
2. **Non-destructive GET:** `take_wav()` is one-shot, which suits the probe but not play-then-save. Add peek semantics: `GET /v1/device/audio` returns the completed WAV without discarding; `DELETE` discards (or cancels if active); retention still bounded by next-arm/disconnect. Update `AudioIngestor` API, its 8 tests, handler tests, and probe expectations (probe's GET-after-DELETE 409 stays valid).
3. **Status capability field:** expose `audio_capture` in `/v1/status` JSON (true when board is `xggf-64x8` and opt-in/token enabled) following the existing derived-field style in `daemon/src/status.rs`/`main.rs`, so apps don't hardcode env knowledge.

**Apps (same PR, Mac + Linux, zh-Hans both sides, then `tools/check-localization.py`):**
4. New client methods on Mac `DaemonClient.swift` and Linux `desktop/src/client.rs`: audio start/stop/stats/WAV/delete.
5. **Recorder card on the XGGF device pages**, following the existing Wi-Fi-provisioning card pattern: sample rate (8/16 kHz, default 16), bounded duration (1–60 s), Start/Stop, live stats polling (frames, lost, terminal error from the 409 body), then **Play** and **Save…**. Mac: `AVAudioPlayer` + `NSSavePanel` (korekore `DevicePage.swift` board card and `SettingsView.swift` DeviceView). Linux: same card in `pages.rs`/`main.rs`; Save via the existing file-dialog mechanism; Play via `rodio` (new dependency) — if playback proves problematic on Linux, ship Save-only there and document the deviation in the PR and READMEs per AGENTS.md.
6. Reword the XGGF Character-page notices only where they now over-claim ("Voice" → "Voice commands" still unsupported; recording is supported on the Device page).
7. Apps never log WAV content; stats text only.

**Docs:** README.md + README.zh-CN.md section-for-section (experimental opt-in speech recording, USB + encrypted Wi-Fi, bounded, in-memory, no default retention); `docs/architecture.md`; `PLAN_XGGF_64X8.md` status; `firmware-xggf/README.md`.

## Risks
- errno-113 may be environmental (AP kicks an idle-ish client); the gate requires classification and a measured mitigation (power-save off or keepalive), not necessarily a firmware rewrite.
- Intermittency costs wall-clock; the 3-sequence stop-rule bounds it.
- Gate 4 needs the user's ears — scheduled checkpoint.
- Linux playback dependency (rodio) is the one place platform parity may need a documented deviation.
