# Lessons learned

## Where a process runs is not the product surface the user wants to go back to

Claude Code can run inside Ghostty, but that doesn't mean K2 should send the user back to the terminal. The first implementation mistook "where the process runs" for "where the user wants to continue the session", and overlooked that the Claude App can already import and open the matching Code session through `claude://resume?session=<UUID>`.

When designing "open the source", first settle the canonical user surface: a conversational Activity returns to its session's App, CI returns to the run page, and only when no session UI exists do you fall back to the terminal. Before implementing, check the deeplinks the target App has registered and the consumer logs on the machine. Don't lower the product goal just because the cwd is easier to get.

## Launching an app is not navigating to the target resource

An external `open` command returning 0 only proves that macOS accepted the URL and activated the app; it doesn't prove the app loaded the target internally. The first acceptance check for K2 only looked at `vibebuddyd`'s "opened" log and missed the `thread not loaded` that the Codex consumer logged right after, so "opened the app" was misreported as "opened the matching session".

Cross-app deeplinks must be verified on both the producer and the consumer side: first confirm the command call succeeded, then check the target app's routing log or visible page. Also distinguish lifecycle identity from navigation identity: a Codex sub-agent's `session_id` is used for activity deduplication, but desktop navigation must use the parent `thread_id` that owns it.

## The navigation source must not be destroyed along with a transient activity

K2 exists to take the user back to what just happened, but the first implementation attached the source only to "working / waiting for input" activities. After `Stop` removed the activity, the screen still showed `DONE`, yet K2 already returned "no activity to open"; a daemon restart also lost the same location.

Activity state and navigation history have two different lifecycles. An activity can end or expire, but the most recent locatable Codex thread, Claude session or CI run should still be kept separately and persisted to the local state file. Regression tests must cover at least two paths: after a task completes and after a daemon restart. Hardware acceptance must press K2 again after the task has finished, not only while it is working.

## Don't source the EIM activation script directly from automation scripts

The `activate_idf_v5.5.3.sh` generated by EIM 0.19.0 reads the caller's `$0`, `$1` and shell variables to decide whether it is being sourced. Called from a Bash script with `set -u`, it may fail first on the undefined `ZSH_VERSION`; even with nounset temporarily off, it misreads the calling script's name as "executed directly" and does `exit 1`.

Automation scripts should run the activation script in its `-e` mode to read the environment variables, then invoke `$IDF_PATH/tools/idf.py` with a fixed Python interpreter. Interactive shells can still source the activation script normally.

## Confirm address semantics before passing an I2C address across components

ESP-IDF's native I2C API uses 7-bit device addresses, but the default I2C control in `esp_codec_dev` 1.6.2 takes an 8-bit wire address and shifts it right by one internally. Detecting the ES8311 at `0x18` with the native API doesn't mean you can pass the same number unchanged to the audio component; that would actually access `0x0c`.

When the hardware adaptation layer wires in a third-party component, confirm the address convention from the component's implementation, and use whatever USB diagnostic channel is available to report, stage by stage, where initialization fails.

## Aggregated state must not swallow one-shot notifications

Codex's `Stop` means a turn has ended, not that the whole session has. Aggregating only by `session_id` and turning `Stop` into a state snapshot of the remaining tasks swallows the completion announcement of parallel tasks; later events may then rebuild the activity, causing delayed or duplicate announcements.

The hook lifecycle must be modeled by `session_id + turn_id`. The screen is persistent state that can be deduplicated; the voice is an edge notification consumed only once per turn. The two must be handled separately, and a repeated event for the same `turn_id` must not trigger the voice again.

`Stop` only means the assistant stopped generating; it doesn't mean the task succeeded. A conversational question also triggers `Stop`. Before announcing success, "waiting for the user to answer" must first be separated from "done". If upstream provides no structured result, do minimal classification inside the privacy boundary and pass only the derived state, never the reply text.

## An external process's lifecycle events are not guaranteed to wrap up

This is the second time we got Codex hook lifecycle modeling wrong. Last time we took `Stop` as the end of the whole session; this time we assumed every activity would eventually receive a `SessionEnd`. When Codex is force-quit it sends no closing event at all, so the abandoned activity occupies a task card forever and pins the pet in the needs-input state, which only a daemon restart can clear.

An external process's lifecycle events are best-effort notifications, not transactions. State created by external events must be able to expire on its own, and cleanup must be driven by a timer, not triggered lazily only when the next event arrives: after the last session disappears, no more events will come. Expiry timeouts must be tiered by what the state means: a "working" with no events usually means the process is dead, while a "waiting for user" with no events only means the user hasn't come back yet. Using one timeout for both forces a choice between losing reminders and never cleaning up.

## "No change" in the visible state is not "no activity"

Deduplication makes `visible_activity` return `None` when the screen hasn't changed. Treating that the same as "there are no activities at all" (`visible_activity().or_else(idle)`) wipes a still-running task off the screen when one session ends while another Agent's screen happens not to have changed.

If a function returning `Option` lets `None` carry two meanings, callers will sooner or later confuse one of them. Existence checks must query the collection directly, never be inferred from "whether any output was produced". This defect already existed in the single-Agent days and only surfaced on real hardware once two Agents coexisted and more sessions were alive at the same time. Concurrency is what develops this kind of bug into view; with only one session in a unit test it never shows up.

## Build targets belong in version control, not in generated files

Flashing firmware from a freshly created worktree failed: the build output targeted esp32 instead of esp32s3. The cause was that `CONFIG_IDF_TARGET` existed only in `sdkconfig`, which is gitignored by ESP-IDF convention; the project fact of which chip we target actually lived only in an untracked file on one machine.

Ignoring generated files is right, but any decision that "must be made correctly again on another machine" has to be recorded in a tracked intent file, here `sdkconfig.defaults`. The test is simple: delete every untracked file and rebuild. If the result changes, some fact has leaked outside version control.

## Hardware acceptance must test the exact binary production loads

After heartbeat and link-loss indication were done and "passed hardware acceptance", the device still kept flashing `NO LINK` during quiet stretches. The acceptance run had used `target/release/vibebuddyd` in the worktree, while the LaunchAgent loaded the file of the same name in the main repo, which had never been rebuilt. The string `device.heartbeat` appeared 0 times in the running process.

So the firmware's 15-second timeout shipped, but the half that sends heartbeats didn't, and the feature was inverted: a feature meant to expose stale state became a constant false alarm itself.

This kind of defect never appears in any test, because the code itself is correct. When accepting a cross-process feature, first confirm that the process you are observing is the one production will load: check the executable path behind the PID, or search the binary for the newly added string. Repos with multiple worktrees are especially dangerous: the same relative path is a different file in each worktree.

The same class of problem came up again that same day, this time in the version label itself: `build.rs` declared that it should rerun only when `.git/HEAD` changes, but a fast-forward only changes `refs/heads/<branch>` and leaves the contents of `HEAD` byte-for-byte unchanged. The build script doesn't rerun, so the binary keeps the previous commit's SHA.

The common root cause is build output silently drifting away from the source state it claims to represent. Any mechanism that stamps source state into the output (version numbers, SHAs, timestamps) must answer for itself "when does this go stale", and you have to actually try it once: change something that doesn't trigger it and see whether the value follows. Freshness you haven't tested is an assumption, and that is exactly where this kind of defect hides.

The third occurrence was on the firmware side (2026-09-15). The FW time in the footer came from `__TIME__` in `esp_app_desc.c`, which only updates when that file itself is recompiled. After changing the button code, doing an incremental build and flashing, the boot banner still reported 11:44, the time of the previous full build. We were using that banner line as proof that "the new firmware is flashed" and it nearly misled us; what settled it in the end were two facts: the ROM-side MD5 during flashing matched the build output, and the output contained the new string. The fix was to have this project generate its own build-time header on every build instead of borrowing another component's compile time. When this lesson was first recorded, only the daemon half was fixed; nobody went back to check whether the firmware had the same problem. The lesson was written as "try every such mechanism once", but in practice only the one that had just broken was tried.

## An output channel with no peer must not wait forever

To support both native USB and the BOX's UART bridge, the firmware writes every diagnostic line to both paths, and the USB Serial/JTAG path used `portMAX_DELAY`. With only the UART bridge connected, there was no host on the USB side pulling data, so once the 1025-byte tx ring buffer filled up, the main task blocked forever in the write function. The screen froze on the last frame, and buttons, link-loss detection and idle animations all stopped with it, while the device just looked like it had "no tasks".

A successful write only means the data left the local buffer, not that a peer exists. Any channel that may have no peer must wait with a finite timeout; if the write doesn't go through, drop that chunk. Incomplete diagnostic output is far better than a frozen main loop.

The Mac side noticed nothing all night, which was the other half of the same mistake: heartbeats only went toward the device, and writing to the serial port always succeeds, so this mechanism built specifically to expose stale state ended up proving only that it was still alive itself. Liveness checks must rely on signals the peer produces, not on your own act of sending.

The same mistake came back on the Mac side (2026-10-01). A new box arrived running someone else's firmware, which never drains its USB serial. `vibebuddyd` wrote a few heartbeats, then blocked in `write_all` forever. The serial worker only checked the flasher's "release the port" signal while idle, never during a write, so flashing failed with `Device or resource busy` and the box could not be rescued from the app. The lesson was written from the firmware's point of view and nobody checked whether the daemon writes to the device the same way. Any wait on a peer must also listen for the signals that ask it to stop waiting. A suspend or cancel signal that is only checked between operations does nothing while an operation hangs.

The length of the fuse is worth noting too: this deadlock only triggered after about 1 KB of accumulated output, which a few minutes of desk debugging never reached, so every acceptance check passed that evening and the bug only showed itself overnight. For any defect that "only breaks once a buffer fills up", acceptance must actually fill the buffer, not just verify that the feature works end to end.

## Before flashing over the UART bridge, confirm large transfers get through

The fix had to be flashed, and the CH343 UART bridge handshook fine and read chip info fine at esptool's default block size, but hit `Checksum error` as soon as it uploaded the stub (1536-byte blocks). `--no-stub` also failed on writing the first flash block, but by then the flash had already been erased, and the device was bricked on the spot: `invalid header: 0xffffffff`. The parameters that work are `--no-stub` plus `FLASH_WRITE_SIZE = 0x100`: slow, but every block passes its checksum.

Erasing happens before writing, so "can it connect" tells you nothing about "can it finish writing". The first flash after changing the connection method should start with a trial write of a small partition (the partition table, say) to confirm the whole path handles large blocks, before touching the bootloader. Otherwise a failed flash doesn't leave things as they were; it leaves a brick.

At the time these parameters lived only in this paragraph, so the next flash meant piecing the command together again. They are now baked into `tools/flash-bridge.sh`, and the order of writing the partition table first, then the app, is in the script's usage too.

## Opening successfully is not opening the right thing

The roadmap recorded K2's ability to open Claude sessions as "both deeplinks verified independently". The evidence was that the app log showed `Resume deep link: importing CLI session …` and then jumped to the `/epitaxy/local_<session_id>` page. The next morning, pressing K2 opened a session whose content stopped at the previous day; pressing it eight times in a row re-imported the whole 5.4 MB transcript every time.

The root cause was using an external system's id as the primary key. The hook reports the **CLI** session id, while the Claude App's desktop session ids live in a different UUID space, and the relationship is one-to-many: when a worktree is deleted and the session moves back to the main repo, on a fork, and on every resume import, another desktop record pointing to the same CLI session appears. `claude://resume` uses that id to claim a transcript on disk, and when the same id has a copy under several project directories it can only pick one.

The most treacherous part was that the original evidence looked like a perfect match: the `local_<session_id>` concatenation lined up precisely because the import itself had created a new session using that very rule. The wrong mechanism produced a result that looked exactly like what we expected. The log had in fact spelled out what it was doing, `importing` rather than `navigating`, but at the time that line was read as evidence of success. Take the words an external system returns literally: they describe the action it actually performed, not the action you hoped it would perform.

Verifying actions like jumping, opening and focusing requires checking the identity of where you landed, not just confirming that "something happened". The usable criterion this time was that the target session's `lastFocusedAt` moved forward with no import log produced; in another scenario it might be a window title or a piece of content unique to the page. This is the same family of mistakes as "a successful write doesn't mean a peer exists": verification stopped at the mechanism level (the call returned, the page moved) and never reached the semantic level (is this the one we meant). Any acceptance check that a vague "success" signal can slip past is not yet an acceptance check.

## Hook scripts run under the system interpreter, not your dev environment

While adding the K2 feature, `tools/codex-hook.py` got a signature of `-> str | None`. The Python used for local development was 3.11, and it ran fine; but `~/.codex/hooks.json` specified `/usr/bin/python3`, which on macOS is 3.9, and PEP 604 union types are evaluated when the `def` executes, so the module couldn't even be imported. From that commit on, every Codex event died on a `TypeError`, and no CX card ever appeared on the device again.

The failure was silent because two layers of design stacked up: the hook script swallows every exception itself so it never disrupts Codex's main flow, and this crash happened at import time, never reaching that try block. Codex only saw a non-zero exit code and won't raise the alarm for you. So the correct design of "don't disrupt the main flow" also guaranteed the failure would never be reported.

For a script invoked by an external host, the runtime interpreter is decided by the host's configuration and has nothing to do with the `python3` in your terminal. Either remove the version dependency in the script (a single `from __future__ import annotations` line is enough) or run it once with the interpreter the host will actually use. The test is simple: copy the command from the config file verbatim, feed it a real payload, and check the exit code.

The same commit left another problem behind too (see the previous entry). What they share is that the change landed on a path we rarely walk, while acceptance only covered the path we walk often. When changing a shared entry point, verify every caller it has.

## Confirm a newly created build directory is ignored before `git add -A`

For hardware acceptance of Leisure mode, a second build directory was created with `idf.py -B firmware/build-fast`. `.gitignore` only had `build/`, which doesn't match `build-fast`. When the feature was done, a single `git add -A` committed 1485 build artifacts, 230,000 lines, together with the feature, and pushed them to the branch and to main. It was only caught at the final `git show --stat` check, and the only remedy was to rewrite the commit and re-push with `--force-with-lease`.

The number `git status --short | wc -l` showed at the time should have raised suspicion, but it was only used to confirm "zero after committing", never checked before committing to ask "why are there so many". For any directory you create yourself, especially one whose name is derived from an already ignored directory, confirm it with `git check-ignore` before committing; before `git add -A`, glance at the count and first few lines of `git status`, and stop if the number looks off. Ignore rules should also be written as patterns: this time we added `build-*/`.

K2 jumped to the wrong session under parallel tasks: one task finished and was announced while another was still running, and the finished activity had already been removed from the card stack, so pressing K2 recomputed the focus, which could only land on the one still alive. The very thing the user had just heard about was the only one that couldn't be selected. The first fix remembered the source that was just announced and gave it a 30-second validity window; that was pointed out as wrong.

The 30 seconds was pulled out of thin air, and it pointed the wrong way to begin with: the whole point of this device is that you aren't at your computer. Go get a glass of water, come back and press K2, and the window has long passed, so the target drifts back to the current task, failing precisely in the scenario where the device should matter most. The right rule is to let events pass the target along like a relay: it always points to the most recently announced thing, until the next announcement replaces it.

The test: before adding a time window to an interaction, ask "is the user guaranteed to be present?" Windows that only make sense while the user is present (debouncing, merging repeated presses) can use a clock; but for features like "help the user find what just happened", how long the user was away is inherently an unpredictable input, and any fixed window assumes they never left.

The converse is worth noting too: a task that is still running stays on screen, and the user can see it just by looking up; they don't need a button to locate it. What really needs locating is exactly what has already disappeared from the screen. When building "quick jump" features, first ask which step it actually saves the user, instead of defaulting to "whatever is newest".

## The UART bridge can't swallow a whole line at once: run a controlled experiment before changing the device

On 2026-09-16, while writing voice packs, lines longer than about two hundred bytes sent to the device through the CH343 bridge arrived corrupted: the length was unchanged, but in every 384 bytes, 32 bytes were replaced by the 32 bytes that followed. We suspected the IDF UART driver's interrupt threshold, the ring buffer and the main task stack in turn, changed the firmware three times to no effect, and along the way overflowed the main task stack once. What actually located it were two steps: having the device echo back the received string verbatim for a byte-by-byte comparison (`device.echo`), then switching to a receive path that bypasses the driver entirely and polls the hardware FIFO directly, as a control. The corruption was identical, which showed the bytes were already wrong before reaching the ESP32, so the problem was in the bridge or the macOS driver. Looking back at the vibebuddyd logs, the device had already reported `invalid_json` more than three hundred times; it's just that most lines were short and nobody paid attention.

The fix was on the sending side: when going through the bridge, write in chunks paced at line rate (after every 128 bytes, wait for them to finish going over the wire); the native USB port is unaffected. Flashing is the same: espflash's fixed 1 KB write blocks can't get through this bridge, so we had to implement the ROM protocol ourselves with 256-byte blocks. Next time a link problem shows up as "content wrong but length right", the first step is to find a controlled experiment that proves which segment the bytes go wrong in, rather than tweaking parameters in whichever layer is most convenient.

## Before rewriting someone else's config file, find out how it treats "modified"

During the rename migration on 2026-09-16, the App automatically rewrote the paths of the six hooks in `~/.codex/hooks.json` from AgentBeacon to VibeBuddy on launch, with a code comment saying "we wrote these ourselves, just replace them, no need to ask again". Codex, however, keeps a `trusted_hash` for each hook under `[hooks.state]` in `config.toml`. Once the file changed, the hashes no longer matched, the entries were judged "modified, pending review", and they silently stopped running until someone re-trusted them with `/hooks` in Codex. From 14:04 the box never made another sound for Codex, and a human only noticed four hours later. During the same period Claude Code worked fine, because it has no such review step and new sessions simply read the new config.

The App's own Agents page showed an orange dot plus "等待第一次事件…（记得在 Codex 的 /hooks 页面信任这份配置）" ("Waiting for the first event… (remember to trust this config on Codex's /hooks page)"). That sentence was word-for-word the same in the healthy and the broken case, so it wasn't a status, it was decoration. Now: if the config file's modification time is newer than the last event the daemon reports, it turns red and says plainly where to go and what to do; and if the migration rewrote the Codex config, a notification pops up on the spot. The App doesn't recompute Codex's hash, which is the other side's internal format and changes with its versions; it only looks at the one fact it can observe itself: whether any event has arrived since the write.

This is the third time Codex hooks died silently (the previous two: the Python 3.9 import failure and the `Stop` semantics). What they share is that Codex never raises the alarm when a hook fails or is disabled, so detection can only be our responsibility. Two rules: before writing to another program's config, find out how it reacts to "the file changed" (trust, hashes, caches, needing a restart); and for any write that needs a human to take an extra step before it takes effect, tell the human at the moment of writing, instead of leaving a permanent line of small print and waiting for them to remember.

How it was pinned down is worth recording too: first, feeding a Codex payload to the hook binary by hand made the daemon record the event immediately, which cleared the binary-to-daemon segment; then, counting hook log invocations in ten-minute buckets put the break precisely at 14:04, matching the time of the migration commit. Cutting the chain into segments that can each prove their own innocence is much faster than tweaking parameters in whichever layer is most convenient.

## An App in daily use must not live in a worktree's build directory

After a system update and reboot, the menu bar icon was gone. The login item recorded a bundle path of `app/build/Vibe Buddy.app` under some feature-branch worktree, and that worktree had long since been deleted along with the repo rename; when launchd can't find the bundle it silently skips it, and there was no second copy of the App anywhere on disk. It had still been running before the reboot only because the process outlived its directory.

This is the flip side of "hardware acceptance must test the exact binary production loads": that one says what's running isn't the new one; this one says what's running has no home at all. Anything the system references persistently (login items, LaunchAgents, absolute paths in hook commands) must point to a location that doesn't come and go with branches. The App's location is `/Applications`, and the packaging script sends it there with `--install`; anything launched from elsewhere counts as in development only. The test: after `git worktree remove`, reboot once; only what is still there counts as installed.

## `cargo fmt -p <package>` formats the whole package, not just the files you changed

On 2026-09-21, while adding host support, I ran `cargo fmt -p vibebuddyd` after finishing the daemon changes. It reformatted all twelve source files in the package: `ci.rs`, `rom_flasher.rs`, `serial_transport.rs` and others that had nothing to do with the change each gained dozens of lines of diff, and `main.rs` had only one line of real change but a 176-line diff. This repo has never been run through rustfmt as a whole, so "formatting along the way" stuffed all the historical style differences into a single feature commit at once, and in review you couldn't tell which lines were real changes.

Reverting cost more than it looked: files that hadn't been touched at all could simply be restored with `git checkout HEAD --`, but in the files that had been changed, noise and real changes were mixed in the same hunks, so they could only be reverted wholesale and redone.

Rule: don't run package-level or workspace-level `cargo fmt` in a repo that has never been formatted uniformly. If you format, format only new files, or use `rustfmt <single file>`. Before committing, check `git diff --numstat`: if the changed line count is far more than you wrote, noise has crept in.

## `sdkconfig.defaults` only takes effect when `sdkconfig` doesn't exist

On 2026-09-22, the first build of the three firmware files needed for the Release package failed in `idf.py build` because the app didn't fit its partition: a 1.47 MB binary in a 1 MB partition. Yet the factory entry in `firmware/partitions.csv` said 4M, and `sdkconfig.defaults` also said `CONFIG_PARTITION_TABLE_CUSTOM=y`.

What was actually in use was the local `firmware/sdkconfig`, which contained `CONFIG_PARTITION_TABLE_SINGLE_APP=y` plus `partitions_singleapp.csv`. ESP-IDF only generates `sdkconfig` from `sdkconfig.defaults` when `sdkconfig` doesn't exist; later changes to the defaults never flow back into it. That sdkconfig predated the custom partition table being added to the repo, so the custom partition table had never taken effect. After deleting it and regenerating, the build passed immediately, with a 4 MB app partition and 64% headroom.

The impact was bigger than one failed build: the firmware running on the device had been flashed with the wrong partition layout, and the `voices` partition declared in the repo didn't exist on that flash at all. Flashing the new firmware rewrites the partition table, so the voice pack has to be rewritten.

`sdkconfig` isn't in git, so this is a trap each machine falls into independently: whoever still has the old copy on their machine is quietly using the wrong config, and CI can never reproduce it, because CI does a clean checkout with no sdkconfig and takes the correct path. The test: when the build output doesn't match the config declared in the repo, first confirm the declaration was actually read in, before suspecting the declaration itself is wrong.

## A worktree living inside the main repo finds config out of bounds when searching upward

On 2026-09-26, while creating the device crate `firmware-rs/device` for the Rust firmware, which needs to be built separately with the Xtensa toolchain, I added an `exclude` to the `Cargo.toml` at the worktree root. `cargo build` then complained that "current package believes it's in a workspace when it's not", pointing at `/Users/dragon/workspace/vibe-buddy/Cargo.toml`, that is, the main repo.

There were two layers to the cause:

- When cargo searches for the workspace root, it doesn't stop at a manifest that excludes the current package; it keeps searching upward.
- This repo's worktrees live under the main repo's `.claude/worktrees/`, so one more level up is the main repo.

So builds in this worktree read the main repo's config, from a different branch.

Any mechanism that "searches upward from the current directory", such as cargo workspaces, `.cargo/config.toml`, `rust-toolchain.toml` and assorted dotfiles, can cross the boundary and read the main repo's files in a nested worktree. A crate built on its own must pin the boundary with an empty `[workspace]` in its own manifest, rather than relying on an `exclude` further up. The test: if a path in an error or log isn't under the current worktree, the search went out of bounds.

## espflash can't parse partition tables with custom data subtypes

The same day, while building the flash image for the Rust firmware, `espflash save-image --partition-table firmware/partitions.csv` panicked outright, at an `Option::unwrap()` in `esp-idf-part`. The cause is that the `voices` partition's subtype `0x40` is a custom value, and `SubType::data()` only recognizes ESP-IDF's predefined enum.

The fix was to stop handing the partition table to espflash and encode it ourselves with `tools/make-partition-table.py`. After encoding, we generate the same CSV once with ESP-IDF's `gen_esp32part.py` and only use ours if the two match byte for byte. The bootloader and app still come from espflash, but the bootloader must be built with `--flash-size 16mb`; otherwise the image header records the default size, and the bootloader treats the `voices` partition beyond 4 MB as out of range.

When you replace someone else's implementation of a format with your own, you must do a byte-for-byte comparison against the original implementation's output; otherwise you've just swapped in an unverified implementation.

## Someone else's App upgrade can quietly take away the process environment we rely on

On 2026-09-28 we found that pressing K2 after a task finished couldn't open the Codex session, and the daemon log always reported "the session has no host window".

K2's target is decided by the hook, and its only basis is `__CFBundleIdentifier`: LaunchServices injects this variable when launching an App, and it is inherited all the way down the process chain to the hook. The problem arose after the Codex desktop App was upgraded to 26.924 and renamed to ChatGPT.app: it clears this variable when launching `codex app-server`, so every Codex session was judged Headless.

We didn't change a single line of code, yet the feature broke without a sound: pressing K2 did nothing at all, leaving only a single WARN line in the daemon log. The last successful opening of a Codex session was on September 17, 11 days earlier.

The fix: when the environment variable is missing, walk up the hook's own process chain to the ancestor launched directly by launchd, and read the bundle id of the outermost `.app` in its path. It has to be the outermost, because ChatGPT.app also embeds a `CodexCLI.app`, which has its own bundle id (`com.openai.codex.cli`) but no window to activate.

Anything that relies on what a host process happens to provide "in passing", such as inherited environment variables, process names or directory structure, is not a contract, and the other side won't notify us when it upgrades. Dependencies like this need two layers of protection:

- **A second basis**: when the primary basis is missing, fall back to a fact guaranteed by the operating system itself, here the process tree and bundle structure.
- **Failures must be visible to a human**: when the result changes from "can jump" to "nowhere to go", someone should know, instead of there being only a WARN line. This one isn't done yet.
